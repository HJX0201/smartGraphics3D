# smartGraphics3D 项目面试 100 问与参考回答

> 适用方向：C++ 桌面客户端、CAD/CAE、三维图形、Qt、系统性能与工程化岗位  
> 项目技术栈：C++17、Qt 5.12.10、OpenCascade 7.7.0、CMake、MSVC、CTest  
> 回答口径：基于当前仓库实现和正式测试结果整理，不虚构团队规模、线上用户量或个人职责。

## 使用方法

这些答案是“可证明的高质量示范”，不是要求逐字背诵。面试时建议保持四段式：

1. 先用一句话给结论；
2. 再解释关键机制；
3. 给出代码、测试或指标证据；
4. 主动说明限制和下一步。

涉及“我负责”“我设计”的内容，只在确实由本人完成时使用。如果项目由多人完成，应明确
自己的代码边界，不能把团队成果全部写成个人成果。

## 一、项目总览与个人贡献（1—10）

### 1. 请用 30 秒介绍一下 smartGraphics3D。

**参考回答：**

smartGraphics3D 是一个基于 C++17、Qt 5.12.10 和 OpenCascade 7.7.0 的 Windows x64
桌面 CAD 应用。我重点解决了 CAD 几何、文档状态和 AIS 显示资源之间的解耦，并实现了
普通复制与共享显示实例两种模式。对于包含 5000 个实体、约 234 万三角形的单一重载
模型，显示 10 份时，共享实例将 Private Bytes 从 1950.91 MiB 降到 499.99 MiB，
估算 GPU 几何从 1876.50 MiB 降到 187.65 MiB。项目有七组自动测试、Debug/Release
构建脚本、性能原始数据和可复现报告。

### 2. 如果给你两分钟，怎么完整介绍这个项目？

**参考回答：**

项目目标是实现一个具备 CAD 文件交换、实体建模、测量、选择、多视口和项目持久化能力
的桌面三维应用。架构上分为 Core、Kernel、Document、Commands、IO、Render、GUI 和
App；Document 是业务状态的唯一所有者，Kernel 封装 OCCT 几何，Render 负责 AIS 和
选择，GUI 只做交互编排。

最有代表性的技术决策是共享显示实例。普通复制虽然共享 `SKernelShape`，但每个
`AIS_Shape` 仍会生成独立 Presentation 和 OpenGL 几何。我增加了
`presentation_group_id`，同组、同几何、同显示属性的对象由一个 `AIS_Shape` 原型和
多个 `AIS_ConnectedInteractive` 显示；平移、旋转保留共享，几何编辑先物化再解除共享。

验证上，我没有只看对象数量，而是生成了一个包含 5000 个实体的大 Compound，只显示
1、2、5、10 份。每种模式在全新进程运行三次取中位数，同时记录进程内存、首显、重绘、
结构数量、展开三角形和 OCCT 原始统计。10 份时 Private Bytes 降低 74.37%，但重绘
基本不变，这也符合“共享几何、不减少绘制实例数”的理论。项目目前是 Beta，Windows
x64、Qt 5.12.10 和 OCCT 7.7.0 是明确兼容边界。

### 3. 这个项目解决的核心问题是什么？

**参考回答：**

它同时解决两个层次的问题。产品层面，是把 CAD 导入、几何操作、测量、视图、撤销和
项目保存组织成可用的桌面应用；技术层面，是处理“大量重复复杂零件”时显示资源随副本
数线性增长的问题。后者不是简单共享 `TopoDS_Shape` 就能解决，因为 AIS Presentation
和底层 Graphic3d/OpenGL 图元仍可能被每个 `AIS_Shape` 独立创建，所以需要在显示层
引入真正的实例化。

### 4. 你在项目中的核心贡献应该怎么讲？

**参考回答：**

我会按实际代码边界回答，而不是泛泛说“负责整个项目”。可以重点讲四部分：第一，设计
Document、Kernel、Render、IO 的模块边界；第二，实现 `presentation_group_id`、
`AIS_ConnectedInteractive` 原型复用和实例选择映射；第三，设计新 `.sg3d` 格式，让
显示组和变换能够保存、撤销与恢复；第四，建立重载基准、七组自动测试和可重复构建脚本。
每一部分都可以定位到具体源码和报告。若某部分不是本人独立完成，要明确说明自己负责的
接口、实现或验证范围。

### 5. 项目中最难的技术问题是什么？

**参考回答：**

最难的不是创建 `AIS_ConnectedInteractive`，而是让共享方案在完整编辑器语义下成立。
实例必须有独立变换、对象 ID、选择 Owner、可见性和冻结状态；颜色、透明度或显示模式
不同又不能错误共享；面、边、点选择还会受到实例 Location 的影响；几何编辑和导出必须
拿到世界坐标下的真实 Shape。我的处理方式是把问题拆成数据模型、AIS 生命周期、选择
映射和物化边界四部分，并分别建立结构测试和持久化测试，而不是只验证“画面看起来一样”。

### 6. 这个项目最有创新性的地方是什么？

**参考回答：**

创新点不是发明实例渲染，而是把 OCCT 的 Connected Presentation 能力完整落到可编辑、
可持久化、可撤销的 CAD 文档模型里。具体包括：显示组 ID、按有效显示属性拆分原型、
单成员退化、实例变换、子形状选择映射、几何操作自动物化，以及对独立 Presentation、
共享原型和 Connected 实例的结构统计。这样优化不是一个孤立的渲染技巧，而是贯穿业务
数据、交互和验证的工程方案。

### 7. 项目当前有哪些主要功能？

**参考回答：**

项目支持 STEP、IGES、BREP、STL、OBJ 的导入导出；支持长方体、圆柱、圆锥、球体、圆环
体以及布尔、圆角、倒角、孔、镜像、变换和阵列；支持对象、实体、面、边、点选择，以及
距离、角度、半径、面积、体积和包围盒测量；支持正交/透视、标准视角、单/双/四视口、
同步相机、剖切和渐进显示质量；还支持 100 步撤销/重做、快照、自动恢复和 `.sg3d`
项目文件。面试时我会先讲与目标岗位最相关的三到四项，不会把功能列表全部背一遍。

### 8. 为什么选择 C++、Qt 和 OpenCascade？

**参考回答：**

C++ 适合承接 OCCT 这类大型原生几何内核，也便于控制对象生命周期和性能；Qt 提供成熟
的 Windows 桌面 UI、事件循环、线程任务、资源和测试框架；OCCT 提供 B-Rep 几何、
STEP/IGES 交换、拓扑运算、网格化和 AIS 交互显示。组合的优势是能较快形成完整 CAD
应用。代价是 ABI、运行库部署、UI 线程边界和 OCCT 类型隔离都需要额外工程设计，因此
项目把 OCCT 类型限制在 Kernel、Render、IO 内部。

### 9. 你怎么证明这不是一个只能演示的 Demo？

**参考回答：**

我看三个证据。第一，功能不是直接堆在窗口类里，而是有明确模块和文档事务，失败能够
回滚；第二，有 Kernel、Document、ProjectCodec、CadCodec、TaskManager、GUI 和
Viewport 七组自动测试，Debug/Release 都通过；第三，性能结论附带确定性测试模型、
SHA-256、24 份原始运行 JSON、汇总和 HTML 报告。它仍是 `v0.1.0-beta.1`，不能宣称
已经达到商用 CAD 的成熟度，但已经具备可维护、可验证和可交付的工程骨架。

### 10. 项目目前最大的限制是什么？

**参考回答：**

当前只正式支持 Windows x64、Qt 5.12.10 MSVC x64 和 OCCT 7.7.0；项目格式仍处于 Beta，
不保证向后兼容。共享实例只适合同几何、同有效显示属性的重复对象，实例一旦缩放或做
布尔、圆角等几何编辑就会物化并解除共享。共享能明显降低显示几何内存，但不能消除每个
实例的业务对象、选择 Owner、变换和绘制开销。主动讲清这些边界，比声称“内存一定减半”
更可信。

## 二、架构与数据模型（11—20）

### 11. 项目为什么要拆成这么多模块？

**参考回答：**

拆分依据是变化原因，而不是目录好看。Core 放无领域依赖的结果类型、单位、坐标和任务；
Kernel 封装几何；Document 管业务状态和事务；IO 管格式适配；Render 管 AIS 与选择；
GUI 只编排用户操作。这样几何内核升级、项目格式变化和 UI 改版不会互相渗透。CMake
目标也按相同边界建立，依赖方向从上层 GUI 指向下层能力模块，避免循环依赖。

### 12. 整个项目最核心的数据流是什么？

**参考回答：**

用户操作先由 GUI 收集参数和预览，随后调用 Kernel 生成或变换几何，再通过 Document
事务提交 `SSceneObject`。Document 发出 `documentChanged`，Render 读取文档对象并同步
AIS；保存时 IO 从 Document 序列化元数据和 BREP。反向选择时，Render 把 AIS Owner
映射回业务对象 ID 和子形状索引，再通知 GUI。关键点是 GUI 和 Render 都不直接拥有
业务真相，Document 才是唯一可信状态。

### 13. 为什么不让 OCCT 类型出现在所有模块的公共接口中？

**参考回答：**

如果 `TopoDS_Shape`、`AIS_InteractiveObject` 到处传播，业务层会与 OCCT 的头文件、
ABI、异常和生命周期强耦合，测试也很难隔离。项目使用 `SKernelShape` 作为不透明值类型，
用纯 Qt/C++ 类型表达变换、显示样式、选择和统计；只有 Kernel、Render、IO 的适配实现
通过访问器拿到底层 Shape。这样不是完全消除依赖，而是把依赖压缩到可替换的边界内。

### 14. 为什么说 `S3dDocument` 是业务状态的唯一所有者？

**参考回答：**

对象列表、项目名、单位、坐标系、历史、快照、撤销栈和修订号都由 `S3dDocument` 保存。
GUI 只持有引用并发起操作，Viewport 订阅文档变化后重建显示，不维护另一份可编辑场景。
这个选择牺牲了部分增量更新效率，但显著降低了“树控件、视口和保存数据互相不一致”的
风险。后续若做增量同步，也应以文档变更集为来源，而不是让视口反向成为状态所有者。

### 15. `SSceneObject` 为什么同时保存 Shape 和 Transform？

**参考回答：**

Shape 表示基础几何，Transform 表示场景实例的位置。把两者分离后，平移和旋转只需更新
矩阵，不必复制或重建 B-Rep，也能让多个对象共享同一基础 Shape 和显示原型。几何编辑、
测量或导出需要真实世界坐标时，再走统一的“物化场景几何”入口合并 Shape 与 Transform。
这种分离是实例化的前提，但要求所有需要真实几何的调用点都不能绕过物化入口。

### 16. `presentation_group_id` 与 Shape 指针有什么区别？

**参考回答：**

Shape 的底层身份只能说明当前进程里几何是否相同，不能表达“业务上允许共享”的持久化
关系，也不能稳定跨保存重开。`presentation_group_id` 是文档级共享意图；渲染时还会
同时检查底层几何身份和有效显示属性。这样既避免仅靠 UUID 错误共享不同几何，也避免仅靠
指针导致重开后丢失分组语义。载入项目时同组几何不一致会按损坏数据拒绝。

### 17. 为什么公共接口使用 `SResult<T>` 而不是直接抛异常？

**参考回答：**

GUI 操作的失败通常是可预期的业务结果，例如参数非法、对象锁定、几何运算失败、文件损坏
或版本不匹配。`SResult<T>` 同时携带错误码、面向用户的消息和诊断详情，让调用链显式
处理失败，也避免 OCCT 异常穿透到 GUI。底层仍会在适配边界捕获 `Standard_Failure`，
转成 `SResult`。代价是调用代码更显式、容易出现忘记检查的问题，所以接口使用
`explicit operator bool()` 并通过测试覆盖错误路径。它也不是编译期强制检查：
调用者若跳过判断直接调用 `value()`，仍可能触发 `std::optional::value()` 异常。

### 18. 文档事务是怎么保证失败不污染状态的？

**参考回答：**

提交前先捕获 `SDocumentState`，然后执行 mutation；如果返回失败，就恢复提交前状态，
不写入撤销记录。如果成功，才截断 redo 分支、保存 before/after、写操作历史、增加修订号
并统一发出变更信号。这是“先执行、失败回滚”的内存事务，不是数据库事务。它适合当前
文档规模；若对象达到更大规模，整状态复制的成本会成为瓶颈，需要演进为命令差量或
copy-on-write。还要注意当前 `commit()` 只处理 mutation 返回的 `SResult` 失败，不在
内部捕获任意 C++ 异常；第三方异常必须先在 Kernel/IO/Render 适配边界转换。

### 19. 撤销/重做和快照有什么区别？

**参考回答：**

撤销/重做是线性的短期操作历史，当前最多保留 100 条，并且在撤销后产生新提交会截断
redo 分支。快照是用户显式命名的长期状态检查点，可以跨越多步操作恢复，创建快照本身
不进入可撤销状态修改。两者都保存对象、单位和坐标系，但语义不同：撤销回答“回退刚才
操作”，快照回答“回到某个业务里程碑”。项目文件会保存展示用操作历史和命名快照，但
重开时会清空运行时 undo/redo 栈，因此不能宣称“重开后还能继续 Ctrl+Z”。

### 20. 为什么后台 CAD 任务默认串行，而不是开满线程？

**参考回答：**

任务管理器虽然使用 `QtConcurrent` 在后台执行，避免阻塞 UI，但调度器一次只启动一个
任务。原因是多个 OCCT 几何操作可能争用资源，而且文档结果必须按提交顺序进入事务；
盲目并行会引入不可预测的内存峰值、线程安全风险和结果乱序。取消使用共享原子标志，
进度通过排队调用回到对象线程。未来只有在证明某些只读、无共享状态的任务可安全并行后，
才会按任务类别开放并发。

## 三、C++17 与 Qt 工程细节（21—35）

### 21. `SKernelShape` 为什么使用 PImpl 和 `shared_ptr`？

**参考回答：**

PImpl 隐藏 `TopoDS_Shape`，避免 OCCT 类型和头文件泄漏到公共接口；`shared_ptr<SImpl>`
让复制 `SKernelShape` 时共享同一个底层包装对象，符合拓扑句柄的共享语义，也让普通复制
本身不会重复深拷贝 B-Rep。这里的共享只覆盖基础几何，不等于共享 AIS Presentation，
这正是后来还需要 Connected 实例的原因。

### 22. `SKernelShape` 的拷贝和移动语义如何设计？

**参考回答：**

它显式提供拷贝构造、拷贝赋值、`noexcept` 移动构造和移动赋值，实际实现采用默认语义。
拷贝增加 `shared_ptr` 引用计数，移动转移控制块，析构由 RAII 自动释放。移动标记
`noexcept` 有利于容器在重分配时选择移动。外部无法直接修改底层 Shape，因此共享包装
不会暴露明显的可变别名问题；原生访问被限制在受控适配层。

### 23. 已经共享了 `SKernelShape`，为什么普通复制仍然很占内存？

**参考回答：**

`SKernelShape` 共享的是 OCCT 拓扑几何包装，而 `AIS_Shape` 的 Presentation、
Graphic3d 结构、三角化显示数组以及底层 OpenGL 缓冲属于显示层资源。为同一 Shape 创建
多个独立 `AIS_Shape`，这些显示数据仍可能逐份生成。因此“业务对象共享 Shape”和
“GPU/Presentation 共享”是两个不同层次，项目用 `AIS_ConnectedInteractive` 解决后者。

### 24. 项目如何表达对象所有权？

**参考回答：**

非 QObject 资源优先使用值语义、`unique_ptr` 或 `shared_ptr`；例如 Kernel Shape 用
共享 PImpl，Viewport 的实现细节用私有实现管理。QObject 依赖 Qt 父子所有权，跨异步
回调观察 QObject 时使用 `QPointer`，避免对象销毁后回调悬空。OCCT Handle 由其引用计数
体系管理。关键不是统一使用某一种智能指针，而是让每个接口明确“所有者、共享者和观察者”。

### 25. `QPointer` 在任务管理器里解决了什么问题？

**参考回答：**

后台任务可能在 `STaskManager` 被销毁后才上报进度。如果 lambda 捕获裸 `this`，排队
回调执行时可能访问悬空对象。代码捕获 `QPointer<STaskManager>`，每次跨线程投递和执行前
都检查是否仍有效，从而把 QObject 生命周期与异步回调解耦。它不能替代线程同步，只解决
QObject 被销毁后的安全观察问题。

### 26. 任务取消为什么使用 `std::atomic_bool`？

**参考回答：**

取消请求由 UI 线程写入，工作线程读取，因此普通 `bool` 会构成数据竞争。共享
`atomic_bool` 提供最小的线程安全取消标志；任务开始前、工作过程中由上下文查询、提交前
都会检查。它是协作式取消，不能强行终止正在执行的 OCCT 调用，所以长操作需要在可分段
位置主动检查，无法检查的单次内核调用仍可能延迟响应。

### 27. 项目如何保证 UI 线程安全？

**参考回答：**

耗时工作通过 `QtConcurrent::run` 放到后台，进度使用 `QMetaObject::invokeMethod` 和
`Qt::QueuedConnection` 投递回对象线程；完成通知由 `QFutureWatcher` 的信号处理。后台
任务不直接操作 QWidget。文档提交也应在受控完成回调中进行。原则是工作线程只计算纯
结果，UI 和文档状态变更回到所属线程。

### 28. Qt 信号槽在项目里承担什么职责？

**参考回答：**

主要承担状态传播而不是业务所有权。Document 在成功提交后发出 `documentChanged`、
`dirtyChanged` 和 `historyChanged`；Viewport 订阅文档变更同步 AIS；任务管理器通过信号
发布开始、进度、失败和完成；GUI 据此更新界面。信号槽减少模块直接依赖，但也可能隐藏
调用顺序，所以关键提交点集中发信号，并用测试验证一次事务只形成一致的最终状态。

### 29. 为什么项目同时使用 STL 容器和 Qt 容器？

**参考回答：**

核心对象集合使用 `std::vector`，与普通 C++ 值语义和连续存储匹配；与 Qt API、信号槽
和 JSON 交互频繁的地方使用 `QList`、`QMap`、`QHash`。选择标准是接口生态和访问模式，
而不是机械统一。跨边界转换会有成本，因此高频路径应避免反复转换；当前文档规模下更重视
清晰性，若性能分析显示容器转换是热点再针对性优化。

### 30. OCCT 异常和项目错误码如何协作？

**参考回答：**

OCCT 可能抛 `Standard_Failure`，项目在 Kernel、Render 或 IO 适配边界捕获，转换成
`GeometryFailure`、`CorruptData` 等 `SErrorCode`。公共层不让异常跨模块传播，GUI
展示简洁消息，并可保留 details 作为诊断信息。这样不会宣称“项目没有异常”，而是把
第三方异常限制在了解其语义的边界内。

### 31. 你如何降低内存泄漏风险？

**参考回答：**

业务对象以值和 RAII 为主；Kernel Shape 使用智能指针；QObject 使用父子所有权；
OCCT 使用 Handle；AIS 清场时按“Disconnect 实例、从 Context 移除实例、再移除原型”
处理；异步回调用 `QPointer`。此外 Debug/Release 测试覆盖重复同步、删除和关闭路径。
这些措施降低风险但不等于形式化证明，进一步可以在可用工具链上增加 ASan 或 Windows
堆分析做长时间循环测试。

### 32. 如何校验实例变换是有效的？

**参考回答：**

文档接口不接受任意 4×4 矩阵，而是检查数值有限、仿射且符合相似变换约束，确保可由
`gp_Trsf` 表达。`S3dDocument::setObjectTransform()` 本身仍允许统一缩放；正式 GUI
操作层会把缩放导向物化入口并解除共享，平移和旋转才直接更新矩阵。也就是说这个约束目前
由高层用例保证，若未来开放 Document API 给插件，应把“仅实例变换”和“缩放物化”拆成
更难误用的接口。Render 转换失败还有防御性回退，但正常数据应在进入文档前被拒绝。

### 33. 为什么资源统计接口不直接返回 OCCT 类型？

**参考回答：**

外部真正需要的是独立 Presentation 数、共享原型数、Connected 实例数、结构数、
展开三角形、估算几何字节和原始文本，而不是操作 `Graphic3d_Structure`。使用
`SRenderResourceStatistics` 这种纯数据结构，可以让 GUI、测试和基准复用统计，同时
保持 Render 边界。它也让结构数量成为自动测试的硬证据，而不是依赖截图判断。

### 34. 读取大项目文件时有哪些资源安全措施？

**参考回答：**

项目格式对元数据和单 Shape 数据设置明确上限，元数据最大 64 MiB、单 Shape 最大
2 GiB；读取前校验扩展名、Magic、格式版本、长度、UUID、矩阵、枚举和几何一致性。
这些限制避免损坏或恶意文件导致无界分配。2 GiB 仍然是较高上限，生产环境还可以增加
项目总大小、对象数、压缩炸弹和解析时间限制。

### 35. 为什么版本号由 CMake 统一生成？

**参考回答：**

如果关于页、诊断包和项目格式分别硬编码版本，发布时很容易不一致。根 CMake 根据项目
版本和 Beta 后缀生成 `s_version.h`，应用和 IO 共用它。这样版本是单一事实来源，也方便
构建系统注入。若未来加入 Git commit，应作为额外构建元数据，而不是替代格式版本。

## 四、CAD 几何、变换与文件交换（36—45）

### 36. CAD 的 B-Rep 几何与屏幕上的网格有什么区别？

**参考回答：**

B-Rep 描述精确的拓扑和曲面，例如顶点、边、线框、面、壳和实体；屏幕显示通常需要把面
离散成三角形。几何运算和 STEP/IGES 交换主要面向 B-Rep，OpenGL 最终消费的是显示网格。
因此共享 `TopoDS_Shape` 不必然共享三角化后的 Presentation，而网格精度也会同时影响
显示质量、生成时间和显存。

### 37. 什么叫“物化场景几何”？

**参考回答：**

物化就是把对象的基础 Shape 与场景 Transform 合并，得到世界坐标下可独立使用的 Shape。
移动和旋转阶段可以只改矩阵以保持实例共享；但布尔、圆角、测量、CAD 导出等必须基于真实
空间几何，因此统一通过物化入口。派生结果采用单位变换和新的显示组，防止旧变换被重复
应用，也防止编辑结果继续错误共享原型。

### 38. 哪些操作可以保持共享，哪些必须解除共享？

**参考回答：**

平移和旋转只改变实例变换，可以保持同一显示原型。缩放、布尔、圆角、倒角、孔、镜像等
会改变几何或后续拓扑语义，因此先物化再生成独立结果；显示组改为新 UUID。颜色、透明度
和显示模式不一定修改几何，但会让渲染键不同，从而拆成不同显示原型。这体现了“业务组
允许共享”和“当前有效属性可以共享”两个条件。

### 39. 为什么缩放不直接作为 Connected 实例变换一直保留？

**参考回答：**

`gp_Trsf` 能表达统一缩放，但 CAD 编辑不只关心画出来的外观。测量值、导出几何、后续
布尔和拓扑索引都需要明确的真实 Shape。如果长期把缩放留在显示变换中，所有下游都必须
正确组合它，容易出现重复变换或漏变换。因此当前策略更保守：缩放时物化并解除共享，用
一定内存换取几何语义一致性。

### 40. 几何运算失败时怎么处理？

**参考回答：**

Kernel 返回 `SResult<SKernelShape>`，调用者先检查输入、执行 OCCT 运算，再检查结果是否
为空和是否通过 `BRepCheck_Analyzer`。GUI 在提交前可显示预览；只有成功结果才进入
Document 事务。失败不会删除输入或写撤销记录。错误消息面向用户，底层异常详情可用于
诊断。对于复杂 CAD，合法输入也可能因容差和拓扑条件失败，所以失败是接口正常分支。

### 41. 为什么同时支持 BREP、STEP、IGES、STL 和 OBJ？

**参考回答：**

BREP、STEP、IGES 更偏精确 CAD 几何交换，STL 和 OBJ 更偏三角网格。支持多格式能覆盖
建模、协作和可视化场景，但不能假设格式能力等价：STL/OBJ 通常丢失精确曲面和丰富拓扑，
从网格重新做高质量布尔也不可靠。IO 模块用 codec 适配不同格式，并把格式差异转换成统一
结果对象和质量提示。

### 42. `BRepCheck_Analyzer` 能保证几何绝对正确吗？

**参考回答：**

它能检查 OCCT 定义下的多种拓扑和几何有效性，是重要防线，但不能证明模型符合所有业务
语义，也不能保证任何后续算法都成功。容差、退化边、自相交和导入器差异仍可能造成特定
操作失败。因此项目把有效性检查、操作返回值、异常捕获和针对性测试组合使用，而不是把
一个 `IsValid()` 当成全部质量保证。

### 43. 导入 CAD 文件后为什么要保留来源和质量信息？

**参考回答：**

`SSceneObject` 保存 source、external path、external reference、quality warning 和
quality message，便于用户知道对象从哪里来、是否存在降级或潜在问题，也方便诊断和
历史追踪。外部路径不能成为唯一数据来源，否则文件移动会破坏项目；正式项目仍保存可恢复
的几何数据，并把外部引用作为元信息。

### 44. 单位和坐标系为什么属于 Document，而不是 GUI？

**参考回答：**

单位和坐标系会影响测量、导入、导出、变换和保存，是业务语义，不是显示偏好。把它们放在
Document 中，事务、快照和项目文件才能一致恢复；GUI 只负责让用户编辑。坐标系还保存
父子关系、到父系变换、来源、校准时间和误差，加载时需要验证 ID 和关系，避免悬空引用
或循环。

### 45. 线性和圆周阵列如何支持两种复制方式？

**参考回答：**

阵列参数包含复制模式。普通阵列为每个结果创建新的显示组；共享阵列继承源对象显示组并
只设置不同 Transform。整个批次在一个文档事务中提交，失败时不留下半个阵列。若源对象
 已经带非单位变换，需要基于明确的矩阵组合顺序生成每个实例，几何编辑型阵列则应走物化
路径。当前共享阵列的最终对象确实复用源 Shape，但后台预览仍逐项生成临时变换几何，
所以最终驻留内存得到优化，创建过程还有减少临时几何的空间。

## 五、OCCT AIS 与共享显示实例（46—65）

### 46. `AIS_Shape` 在 OCCT 中负责什么？

**参考回答：**

`AIS_Shape` 是把 `TopoDS_Shape` 接入交互显示框架的对象，负责根据显示模式、颜色、
透明度、网格精度等生成 Presentation，并参与选择。它不是 Shape 本身。创建多个
`AIS_Shape` 即使底层 Shape 相同，也可能分别计算和保存显示结构，所以普通复制的主要
内存增长发生在这里。

### 47. `AIS_ConnectedInteractive` 是什么？

**参考回答：**

它是连接到已有 Interactive Object Presentation 的实例对象，可以复用源对象的显示
图元，同时拥有自己的局部变换和交互身份。项目为每个共享组创建一个 `AIS_Shape` 原型，
再为每个业务对象创建一个 Connected 实例。这样几何显示数据按原型保存一次，实例只保留
连接结构、变换和选择相关状态。

### 48. 项目究竟共享了什么 OpenGL 数据？

**参考回答：**

项目不在业务层手工共享 VBO，而是通过 OCCT AIS/Graphic3d 的连接结构复用原型
Presentation 中的图元和几何缓冲。`AIS_ConnectedInteractive` 仍然对应独立可绘制结构，
但几何数组不需要为每个实例重复生成。是否落成具体 VBO、何时上传由 OCCT OpenGL 后端
管理，因此报告同时提供结构硬证据和“估算 GPU 几何”，不把估算值冒充驱动层实测显存。

### 49. 渲染器如何决定哪些对象能够共享？

**参考回答：**

渲染键至少包含 `presentation_group_id`、颜色、有效透明度、全局显示模式和底层
`TShape` 身份。只有键完全相同的可见对象才进入同一组。UUID 表达业务共享意图，
`TShape` 防止同组错误几何，显示属性防止复用错误 Presentation。这个规则偏保守，宁可
少共享也不能显示错误。

### 50. 为什么一个共享组只有一个可见成员时要退化？

**参考回答：**

一个成员时创建“原型 + Connected 实例”没有几何复用收益，反而多一个连接结构。因此
直接显示独立 `AIS_Shape`。这也是重载测试中 1 份普通与共享内存几乎相同、结构均为
`1/0/0` 的原因。第二个同组可见对象出现后，场景同步会重建为一个原型加两个实例。

### 51. 同组对象颜色不同会发生什么？

**参考回答：**

它们会因为渲染键不同而拆成多个原型组。颜色、透明度和显示模式会影响 Presentation，
强行共享可能导致显示错误。当前实现选择按有效属性分组，保证正确性；代价是属性越离散，
共享率越低。准确地说，当前颜色和对象透明度参与对象分组，而显示模式使用视口的全局模式，
`SSceneObject::display.mode` 尚未独立参与键。若未来支持实例级材质或对象级模式，应先
补齐这一契约再扩大共享。

### 52. 原型为什么不直接作为场景中的第一个对象显示？

**参考回答：**

共享组统一使用未作为业务实例展示的 `AIS_Shape` 原型，所有业务对象都对应 Connected
实例，这样实例语义一致，业务 ID、变换和选择映射不会出现“第一个对象特殊”的分支。
原型由 Context/连接关系提供 Presentation 来源，但不代表某个业务对象。代价是多一个
原型管理对象，不过几何只计算一次。

### 53. 删除或清场时为什么要先 `Disconnect()`？

**参考回答：**

Connected 实例引用原型 Presentation。清理顺序是先遍历业务实例，Connected 对象执行
`Disconnect()` 并从 Context 移除，再移除共享原型，最后清空容器。这样显式解除依赖，
避免释放顺序不清造成悬空连接或资源延迟释放。顺序也通过删除和场景重复同步测试验证。

### 54. 每个实例如何拥有独立位置？

**参考回答：**

每个 `SSceneObject` 保存独立 `QMatrix4x4`。同步场景时将其转换为 `gp_Trsf`，调用
`AIS_ConnectedInteractive::Connect(prototype, transform)`。因此原型几何和
Presentation 相同，但每个实例在不同位置绘制。变换校验在文档边界完成，转换失败还有
防御性回退，正常路径不会依赖异常纠正数据。

### 55. 共享实例如何保持对象级选择？

**参考回答：**

每个 Connected 对象都是独立的 Interactive Object，`SDisplayedObject` 记录业务对象
ID、当前 Presentation、源 Shape、是否 Connected 和冻结状态。命中 AIS Owner 后先找到
具体实例记录，从而确定业务 ID；再处理子形状映射。不能只从原型反查，因为所有实例共享
同一个原型。

### 56. 为什么子形状选择要用 `TShape/IsPartner`？

**参考回答：**

实例 Location 不同后，命中的面或边可能带有不同位置，直接用完整 Shape 相等比较容易
失配。`IsPartner` 判断两个 Shape 是否共享底层 `TShape`，忽略 Location 和 Orientation
差异，因此可以把实例命中的子形状映射回原型枚举中的稳定索引。前提是拓扑没有被改写；
一旦几何操作产生新拓扑，结果会进入新的显示组并重新建立索引。当前源码已实现这条映射，
但自动测试主要覆盖对象级实例选择和选择模式，真实鼠标命中后的面/边/点索引测试仍应补强。

### 57. 共享实例移动后会不会影响其他实例？

**参考回答：**

不会。移动和旋转只更新目标 `SSceneObject` 的 Transform，原型 Shape 和其他对象矩阵
不变。场景同步时每个 Connected 实例使用自己的转换。自动测试还要验证变换后显示组 ID
不变、实例数量不变、选择仍返回目标对象 ID，这比只看视觉位置更可靠。

### 58. 隐藏、冻结和锁定有什么区别？

**参考回答：**

隐藏决定对象是否进入可见渲染分组；冻结保留显示但停用选择；锁定属于文档编辑约束，阻止
会修改对象的操作。它们是不同层次的语义，不能用一个布尔量代替。隐藏成员变化可能让共享
组从多成员退化为独立 Presentation；冻结只改变激活状态，不应破坏共享关系。

### 59. 全局显示模式变化时共享如何保持正确？

**参考回答：**

显示模式使用视口级全局状态。模式变化时不会为每个 Connected 实例逐个 Redisplay：
普通对象逐个更新源 `AIS_Shape`，共享对象跳过实例，只对每个共享原型设置线框、着色、
透明或边界并 Redisplay 一次。这正是原型复用的收益之一。另一方面，普通文档变更仍会
触发 `synchronizeScene()` 全量清场重建；后续应把对象增删、变换和属性修改做成增量路径。

### 60. 渐进显示质量解决什么问题？

**参考回答：**

超大 Shape 使用高精度网格会让首次显示成本很高。策略根据三角形规模识别大模型，在交互
阶段使用更大的偏差系数，降低网格密度和等待时间；应用默认开启。正式对比基准则关闭该
策略，确保普通和共享模式使用完全相同的固定三角形数，否则网格质量差异会污染内存结论。

### 61. `SRenderResourceStatistics` 统计了什么？

**参考回答：**

它统计独立 Presentation、共享原型、Connected 实例、Graphic3d 结构、展开后的场景
三角形、估算 GPU 几何字节和 OCCT 原始统计文本。结构数量用于证明代码确实进入共享路径；
展开三角形用于证明两种模式画了同等场景；进程内存和估算几何用于量化收益。不同指标回答
不同问题，不能只挑一个最漂亮的数字。

### 62. GPU 几何内存为什么按每三角形 84 字节估算？

**参考回答：**

这是项目定义的统一估算口径，用三角形数量乘固定字节数来比较几何数据随副本数的增长，
不是从显卡驱动读取的真实显存。它的价值是同一网格、同一公式下能验证普通模式约为 N 倍、
共享模式约为一份。84 字节包含项目对顶点/法向/索引等显示数据的保守估算，具体驱动的
对齐、缓存和重复顶点会不同，所以报告明确写“估算 GPU 几何”。

### 63. 如何证明不是只改了统计数字，没有真正共享？

**参考回答：**

结构测试直接检查真实 AIS 结构。10 份普通模式是 10 个独立 Presentation、0 个原型、
0 个 Connected；共享模式是 0 个独立、1 个原型、10 个 Connected。创建代码实际调用
`Connect(prototype, transform)`，清理代码实际调用 `Disconnect()`。同时 Private
Bytes 和首显随结构变化显著下降，三角形总数保持相同。这些独立证据共同排除了“只改公式”
的解释。

### 64. 为什么共享后 30 帧重绘几乎没有变快？

**参考回答：**

共享减少的是几何存储和 Presentation 构建，不是绘制位置数量。10 个实例仍需要执行
10 次实例变换和绘制提交，像素覆盖、深度测试和片元成本也没有消失。因此 30 帧中位数
从 950.41 ms 到 950.69 ms，差异只有 +0.03%，应视为基本不变。这个结果反而说明报告
没有把内存优化夸大成渲染吞吐优化。

### 65. 如果用户编辑一个实例的几何，会发生什么？

**参考回答：**

几何操作先把该实例的基础 Shape 和 Transform 物化，再生成新的 Shape、单位 Transform
和新显示组 ID。它随后拥有独立 Presentation，不会修改其他实例。原共享组剩余成员继续
共享；如果只剩一个可见成员则退化。这个 copy-on-edit 语义让实例默认轻量，但编辑结果
保持独立和可预测。

## 六、性能测试与结果解读（66—80）

### 66. 基准测试使用的算法和正式软件完全一样吗？

**参考回答：**

核心渲染算法完全共用正式的 `S3dDocument` 和 `SOccViewport`，最终都进入同一个场景
同步、分组和 `AIS_ConnectedInteractive` 创建代码，不存在测试专用的假共享实现。但
基准为了稳定，直接构造与复制结果等价的文档对象，没有执行 GUI 预览和点击流程；同时
关闭应用默认的渐进质量以固定三角形数。因此共享结构和资源结论可代表正式软件，GUI
操作耗时和默认质量下的绝对首显时间不能直接等同。

### 67. 5000 实体测试集是怎么生成的？

**参考回答：**

基准用长方体、圆柱、球体和圆环体四类确定性几何，以固定网格布局、偏移和旋转生成
1250 个组合，共 5000 个实体，再组成一个 Compound 并写成 BREP。文件大小
8,288,682 字节，每份固定网格有 2,342,442 个三角形，SHA-256 为
`c15e8cfa063a681bd2c76c62485d64018d4de78ab833e4d394353e8e0e8160d7`。
它不包含客户模型，也没有第三方模型授权风险。

### 68. “5000 个测试集”和“5000 个实体”有什么区别？

**参考回答：**

正式方案是一个重载测试集，内部包含 5000 个实体，再把这个大模型显示 1、2、5、10 份；
不是准备 5000 个小文件，也不是复制一个小零件 5000 次。这样能在较少实例数下放大每份
Presentation 的几何成本，更贴近“少量但很重的重复总成”，也避免每实例管理开销掩盖
几何共享收益。

### 69. 为什么重载测试只做 1、2、5、10 份？

**参考回答：**

目标是验证单个高复杂度模型重复显示的内存复用，而不是靠几千个实例制造极端数字。每份
约 234 万三角形，普通模式 10 份的 Private Bytes 已接近 2 GiB，足以观察线性增长；
继续增加会放大机器内存、驱动和超时风险，降低可复现性。小模型另有 1、10、50、100 份
趋势测试，两类基准分别覆盖几何重量和实例数量。

### 70. 为什么每种情况要在全新进程运行三次取中位数？

**参考回答：**

全新进程隔离上一次运行的 OCCT 缓存、堆保留、GPU 资源和场景顺序影响；三次中位数能
降低偶发调度、窗口曝光和后台负载造成的极值影响。三次不是严格统计学保证，但对工程回归
比单次可靠。性能数字不作为 CTest 硬门槛，硬门槛放在结构正确性；若用于正式论文级结论，
还应增加样本数、预热、置信区间和独立硬件复测。

### 71. 请解释 10 份重载模型的测试结果。

**参考回答：**

普通模式 Private Bytes 1950.91 MiB，共享模式 499.99 MiB，降低 74.37%；Working Set
从 998.65 MiB 降到 416.64 MiB，降低 58.28%；估算 GPU 几何从 1876.50 MiB 降到
187.65 MiB，降低 90%；首次显示从 18099.88 ms 降到 8563.87 ms，降低 52.69%。
结构由 `10/0/0` 变为 `0/1/10`。30 帧重绘几乎不变，说明收益集中在显示数据存储和首次
构建，而不是减少场景中实际绘制的十个位置。

### 72. 理论上共享后内存不是应该直接减半吗？

**参考回答：**

只有两份实例且只看“可共享的几何资源”时，理论上才是从两份降为一份，也就是减少 50%。
N 份时该部分理论减少是 `1 - 1/N`：2 份 50%、5 份 80%、10 份 90%。进程总内存还包含
Qt、OCCT 拓扑、文档对象、选择、变换、连接结构、堆和驱动映射，所以 Private Bytes 不会
按这个公式精确变化。10 份实测的 GPU 几何估算正好降低 90%，Private Bytes 降低 74.37%。

### 73. 为什么共享模式的估算 GPU 几何在 2、5、10 份时不增长？

**参考回答：**

因为这些对象进入同一个显示组，只保留一个原型的几何数组。每个 Connected 实例增加的是
连接和变换，不重复计算几何估算。普通模式分别是 375.30、938.25、1876.50 MiB，近似
按份数线性增长；共享模式都约 187.65 MiB。实际驱动仍可能为每实例维护少量状态，因此
“几何估算不增长”不等于“GPU 总占用完全不增长”。

### 74. 为什么 Private Bytes 的降幅小于 GPU 几何估算？

**参考回答：**

Private Bytes 是进程提交的私有虚拟内存总量，除了显示几何，还包括 B-Rep、Qt 控件、
OCCT Context、选择 Owner、每实例矩阵、Graphic3d 连接结构、线程栈、分配器保留等。
共享只消除其中可重复的 Presentation 几何，所以总量降幅一定受其他固定项和线性项稀释。
这也是不能只凭理论 `1 - 1/N` 推导进程内存的原因。

### 75. Private Bytes 和 Working Set 有什么区别？

**参考回答：**

Private Bytes 表示进程私有提交内存，更适合观察进程为对象承担的内存承诺；Working Set
表示当前驻留在物理内存中的页面，会受系统回收、文件映射和采样时刻影响。重载 10 份时
两者分别降低 74.37% 和 58.28%，方向一致但比例不同。报告同时给出二者，是为了避免用
单一 Windows 内存指标下结论。

### 76. “估算 GPU 几何”能当作真实显存数据吗？

**参考回答：**

不能。它是基于真实三角形数量和固定每三角形字节数的可重复估算，用于比较增长规律。
驱动可能压缩、对齐、延迟上传、共享或在系统内存中保留副本，真实专用显存需要 DXGI、
厂商工具或 GPU profiler 测量。我的结论会表述为“证明几何资源结构从 N 份变成 1 份，
估算减少 90%”，不会说“显卡任务管理器一定下降 90%”。

### 77. 如何保证普通和共享模式画的是同样复杂的场景？

**参考回答：**

两种模式加载同一个带哈希的 BREP，按相同位置生成同样数量对象；基准关闭渐进质量，固定
网格；每档记录展开后的 `renderedTriangles`，并验证两种模式相同。共享只改变 Presentation
组织方式，不减少实例数或每实例可见三角形。需要主动说明一个原始数据瑕疵：
`independent-1-1` 首次生成数据集的冷运行记录为 2,304,840 个三角形，而其余正式运行
为 2,342,442；1份和10份的中位数结论不受影响，10份对比的三角形完全一致，但报告中
“每次完全相同”的说法过强。下一版应预先生成数据集，并在每轮开始前把三角形不一致直接
判为无效运行。

### 78. 为什么 1 份时共享模式反而略高？

**参考回答：**

一个成员会退化为独立 `AIS_Shape`，并没有共享路径；474.89 MiB 与 473.47 MiB 的差异
属于进程、窗口曝光、分配器和运行噪声，三次中位数也不能消除全部波动。正确解读是“1 份
无收益”，不是共享算法负优化。共享收益从第二个同组可见成员开始。

### 79. 为什么共享后首次显示时间也下降？

**参考回答：**

普通模式需要为每个 `AIS_Shape` 计算或建立 Presentation；共享模式主要计算一次原型，
再创建轻量 Connected 结构，因此 10 份首显从约 18.10 秒降到 8.56 秒。它没有接近
十分之一，因为还存在 BREP 载入、三角化基础成本、十个实例结构、选择准备、窗口和驱动
提交等固定或线性开销。

### 80. 当前基准还有哪些不足？你会怎么改进？

**参考回答：**

当前基准的优势是同一正式渲染路径、固定数据、全新进程、中位数和原始记录；不足是只有
一台机器、三次样本、GPU 内存为估算，而且直接构造最终文档对象，没有从 GUI 复制入口
执行，30帧也只是静止窗口的 `repaint + processEvents`，不能代替相机交互 FPS。下一步
我会先预生成并校验每轮网格，修掉首次冷运行三角形异常；再增加两组验证：一组从一个源
对象调用正式 `copyObjects()`，另一组保持应用默认渐进质量。同时接入 GPU profiler、
更多硬件和置信区间，但继续把结构正确性与易波动性能阈值分开。

## 七、项目格式、事务与可靠性（81—88）

### 81. `.sg3d` 项目格式如何设计？

**参考回答：**

文件以 Magic `SGRAPH3D` 和格式版本 3 开头，保存 JSON 元数据以及每个对象的 BREP
二进制数据。元数据记录项目、单位、坐标系、对象属性、Transform、
`presentationGroupId`、历史和快照。读取过程先校验容器边界和元数据，再反序列化 Shape
并执行跨对象一致性检查。格式版本与应用版本分离：应用可以升级，但只有格式发生不兼容
变化时才增加格式版本。

### 82. 为什么不只保存 STEP 或 BREP？

**参考回答：**

单独 CAD 文件只能表达几何，不能完整保存对象名称、可见性、锁定、显示样式、场景变换、
显示共享组、坐标系、历史和快照。`.sg3d` 是应用项目容器，BREP 是其中的几何载荷。
导出 STEP/IGES/STL/OBJ 面向外部交换，项目保存面向无损恢复应用状态，两者职责不同。

### 83. 保存重开后如何恢复共享关系？

**参考回答：**

每个对象保存 `presentationGroupId` 和 Transform。加载时按组校验其序列化基础几何
一致，并让同组对象复用第一份 `SKernelShape`；渲染时再结合颜色、透明度、显示模式和
底层几何身份建立原型。因此共享语义不是依赖进程内指针碰巧相等，而是有持久化 ID 和加载
校验支撑。当前文件写出阶段仍为每个对象重复序列化 BREP，所以它优化的是加载后的内存和
显示资源，不代表 `.sg3d` 磁盘体积已经去重；后续可增加“组级几何表 + 对象引用”。

### 84. 为什么当前明确拒绝旧格式，而不是自动兼容？

**参考回答：**

当前是 Beta，格式和产品命名经历过不兼容调整。与其保留未经充分验证的隐式迁移分支，
不如明确只接受 `.sg3d`、`SGRAPH3D` 和版本 3，遇到旧扩展或旧 Magic 返回可识别错误。
这样兼容边界清楚，也避免错误解析。正式版若承诺兼容，应建立逐版本迁移器和历史样本库，
而不是简单放宽校验。

### 85. 如何处理损坏或恶意项目文件？

**参考回答：**

读取时检查扩展名、Magic、版本、流状态、字段类型、UUID、对象重复、父子和坐标系引用、
矩阵有限性、Shape 大小上限及 BREP 反序列化结果；同组几何不一致直接按损坏项目拒绝。
只有完整解析和验证成功后，才用 `replaceAll` 替换当前文档，避免半载入状态。还可以继续
增加模糊测试和项目总解压上限。当前对单 Shape 有 2 GiB 上限，但读取长度前缀数据时
Qt 可能先分配、随后才核对实际大小；面对完全不可信输入，还应增加项目总预算、流式读取
和校验和，不能把当前实现描述成完整的恶意文件沙箱。

### 86. 为什么保存使用 `QSaveFile`？

**参考回答：**

`QSaveFile` 先写临时文件，成功后原子提交，能降低程序崩溃、磁盘不足或写入失败导致原
项目被截断的风险。只有全部序列化完成并 `commit()` 成功才替换目标。它不能防止磁盘或
文件系统的所有故障；当前也不是带 `fsync`/WAL 的耐久性协议，因此应用仍需要自动恢复、
错误提示和必要的多代备份策略。

### 87. 撤销、快照和保存如何保证实例组不丢失？

**参考回答：**

`presentation_group_id` 和 Transform 都属于 `SSceneObject` 状态；文档的 capture/
restore、快照记录和项目序列化都复制或写出完整对象。因此移动实例、撤销、恢复快照和
保存重开后，分组关系都能恢复。自动测试覆盖这些路径，并包含同组几何不一致的错误分支。

### 88. CAD 导出为什么必须走物化入口？

**参考回答：**

项目对象可能共享基础 Shape，但各自有非单位 Transform。如果导出器直接写基础 Shape，
所有实例会重叠在原点；如果既提前修改 Shape 又再次应用矩阵，会重复变换。统一物化入口
明确只合并一次，然后交给格式 codec。测量和几何预览也使用同一原则，避免不同功能对
“对象真实位置”有不同理解。

## 八、构建、测试与发布工程（89—96）

### 89. 项目的构建工具链是什么？

**参考回答：**

根 CMake 使用 C++17，要求 64 位，精确查找 Qt 5.12.10 和 OCCT 7.7.0；MSVC 启用
`/W4 /permissive- /Zc:__cplusplus /utf-8`。Debug 和 Release 各有独立 Python
入口，自动检测 VS 2022、Windows SDK、CMake、Ninja、Qt 和 OCCT，执行构建、七组
CTest 和运行库部署。项目还可生成不含 Qt 的独立工具链附件，便于复现固定 OCCT/CMake/
Ninja/Python 环境。

### 90. Qt 自动发现如何避免选错 Kit？

**参考回答：**

查找顺序是命令行、项目环境变量、`QTDIR/CMAKE_PREFIX_PATH`、PATH 和常用安装目录；
候选必须满足 Qt 5.12.10 和 x64 PE 位数，Qt 6 与 x86 会在发现阶段明确拒绝。目前脚本
还没有查询 `QMAKE_SPEC/QMAKE_XSPEC` 来直接证明是 MSVC Kit，因此 MinGW x64 可能在
后续 CMake/链接阶段才失败。更完整的实现应在候选验证时检查 compiler spec 和 MSVC
import library，并给出准确的 ABI 拒绝原因。这是当前自动发现仍需补齐的边界。

### 91. `windeployqt` 不可用时怎么办？

**参考回答：**

脚本优先调用与所选 Qt Kit 同目录的 `windeployqt`。缺失或执行失败时，回退到内置最小
依赖清单，复制程序实际需要的 Qt DLL、`platforms/qwindows.dll`、图像/图标插件和
OpenGL 相关组件，再校验平台插件。审查发现当前回退清单包含 Core/Gui/Widgets/Svg，
但 `sgraphCore` 还链接了 `Qt5::Concurrent`，因此极端回退路径可能漏掉
`Qt5Concurrent[d].dll`；正式路径使用 `windeployqt` 已通过，但不能把当前 fallback
夸成完整闭包。发布前应补齐该 DLL，并让测试基于主 EXE 的 PE 依赖逐项断言。完全找不到
Qt 时则停止并列出候选和修复参数。

### 92. 为什么最终放弃 32 位构建？

**参考回答：**

发布工程不能只看代码能否生成 x86，而要保证 OCCT、Qt、MSVC ABI、第三方库和全部测试
都具备同等级验证。当前可用 OCCT 7.7.0 工具链和正式测试基线是 x64，因此根 CMake
直接拒绝非 64 位，文档也只承诺 Windows x64。与其提供未经验证的 32 位脚本，不如缩小
支持面；将来只有获得完整 x86 依赖并通过相同测试矩阵才恢复。

### 93. 七组自动测试分别验证什么？

**参考回答：**

Kernel 测几何创建、变换和运算；Document 测事务、复制、阵列、变换、撤销与快照；
ProjectCodec 测保存重开、版本、损坏数据和实例组；CadCodec 测标准格式；TaskManager
测排队、取消和重试；GUI 测动作和交互状态；Viewport 测 AIS 结构、选择映射、属性和
场景同步。其中 Viewport 已覆盖对象级实例选择、选择模式和资源结构，但面/边/点的真实
鼠标命中索引还不是完整自动化覆盖。另有四组 Python 构建脚本测试，覆盖 Qt 发现、
版本/位数拒绝和部署回退。

### 94. 为什么性能数字不设成 CTest 硬门槛？

**参考回答：**

进程内存和毫秒数会受到驱动、系统负载、窗口曝光、CPU 频率和机器配置影响，硬设百分比
容易产生假失败。CTest 的硬门槛是功能和结构：组 ID、物化语义、选择正确、普通模式 N
个独立 Presentation、共享模式一个原型加 N 个 Connected。性能基准保存原始数据和
趋势，由发布报告判断。稳定结构做硬断言，易波动指标做受控观测。

### 95. 除单元测试外还做了哪些质量检查？

**参考回答：**

Debug/Release 都使用高警告级别构建并通过七组测试；执行 clang-format dry-run 和
clang-tidy；自研 C++ 文件限制 800 行，接近 700 行按职责拆分；检查正式源码没有旧产品
名、本机绝对路径、密钥、客户数据和构建产物；发布目录验证主程序、Qt 平台插件和实际
OCCT DLL 依赖闭包，同时确保测试程序不混入 `bin`。

### 96. 如何保证别人能复现你的结果？

**参考回答：**

仓库提供独立 Debug/Release 构建脚本、明确版本、工具查找顺序、测试命令和性能复现说明；
重载 BREP 在仓库中有固定大小与 SHA-256；每种模式三次原始 JSON、汇总 JSON、Markdown
和 HTML 报告都保留。工具链附件记录版本、许可证和文件哈希，但 Qt 要求用户安装。仍需
承认硬件和驱动会影响绝对性能，所以复现目标是结构和趋势一致，不要求毫秒数逐位相同。
当前仓库状态是本地整理和验证完成，尚无首个 Git commit、remote 和 GitHub Actions，
所以不能提前说“GitHub CI 已通过”。另外 `LICENSE` 是保留全部权利，只能称“公开源码/
source-available”，不能称为 OSI 意义上的开源软件。

## 九、故障、取舍与综合追问（97—100）

### 97. 你遇到过什么典型故障？如何定位？

**参考回答：**

一个典型问题是 Debug 程序启动时报“Qt platform plugin could not be initialized”，即使
目录里能看到 `windows` 插件。定位不能停在“有 qwindows.dll”，还要检查插件实际目录
是否为 `platforms/qwindows.dll`、插件与 QtCore 是否来自同一 Kit、Debug/Release
后缀是否匹配、PE 位数和 MSVC ABI 是否一致，以及依赖 DLL 是否闭合。项目因此把
`windeployqt` 和回退部署都集成到构建脚本，并对缺失、失败和错误候选建立自动测试。

### 98. 为什么选择 AIS Connected，而不是自己管理 OpenGL VBO 实例化？

**参考回答：**

直接 OpenGL instancing 可能获得更细的 GPU 控制，但会绕开 AIS 的显示模式、选择、
高亮、剖切、视图和 OCCT 网格生命周期，需要自己维护 B-Rep 子形状到 GPU primitive 的
映射，工程成本和正确性风险很高。`AIS_ConnectedInteractive` 能在现有 AIS 框架内复用
Presentation，是当前约束下性价比更高的方案。若未来场景以超大规模只读实例为主、AIS
提交成为瓶颈，才值得设计专用 OpenGL 渲染通道，并保留 CAD 选择的回退路径。

### 99. 如果继续优化，你最先做什么？

**参考回答：**

我会先用数据选择方向，而不是直接改代码。第一，增加正式复制入口和默认渐进质量的端到端
基准；第二，用 GPU profiler 获取真实专用显存、上传时间和 draw-call 数据；第三，把
当前全量 `synchronizeScene()` 分析成可增量更新的变更集，避免单个变换触发全部 AIS
重建；第四，评估选择 Owner 和子形状敏感结构的内存。只有确认瓶颈后，才考虑缓存原型、
异步网格化或专用 instancing。

### 100. 这个项目最能证明你具备什么能力？如果重做会改什么？

**参考回答：**

它最能证明我能把一个底层优化做成完整工程闭环：先区分 B-Rep 共享与 Presentation
共享，再设计文档模型和 AIS 生命周期，处理选择、变换、编辑与持久化，最后用结构测试和
重载基准验证，且诚实说明重绘没有提升、GPU 数据是估算。若重做，我会更早建立增量文档
变更协议和端到端基准，把大状态复制式撤销设计成可演进的命令差量，并在接口稳定前建立
历史格式样本。我的优势不只是“会调用 OCCT API”，而是能解释机制、比较方案、处理失败
路径并用证据交付。

## 十二、五个容易失分的说法

1. 不要说“共享后内存一定减半”；应说明 `1 - 1/N` 只适用于可共享几何部分。
2. 不要说“GPU 显存实测降低 90%”；当前是结构证明加统一口径的 GPU 几何估算。
3. 不要说“共享让帧率显著提升”；30 帧重绘实测基本不变。
4. 不要说“基准和用户点击流程完全一样”；核心渲染相同，但基准绕过 GUI 并关闭渐进质量。
5. 不要说“项目已经商用成熟”；当前是有完整工程验证的 Beta 版本。
